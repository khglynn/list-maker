## Music quality (from ROADMAP §3, still true)
- SOP: "feat./ft." format mismatches (~130), fuzzy search for major artists (~80), mark unavailable (~25), then re-sync. TAL: the same pass on its NOT_FOUND set.
- `songs` uniqueness constraint: three true duplicate pairs exist (trailing-space titles, identical Spotify ids); delete the three extras, then apply `pipeline/scrapers/ai_daily/sql/008_songs_unique_per_episode.sql`.

- **SOP's quote-format song parser stores the bullet and the comma in the artist** (found 2026-09-04 by Phase 5's frozen-fixture tests, PR #48): on pages where the Songs Discussed list uses the `- Artist, "Title"` form, `parse_songs_discussed`'s fallback branch yields `artist = '- Dolly Parton,'`. Live: 78 SOP song rows carry that shape, and 77 of them still matched HIGH because the fuzzy score tolerates it — so the damage is cosmetic in Neon, not in the playlist. Fix when convenient: strip the leading `- ` and trailing comma in the parser (with the fixture already in `tests/fixtures/music/sop-episode-quote-format.md`), then one `UPDATE songs SET artist = regexp_replace(...)` over those 78 rows as Kevin's paste.

- **A genuinely songless TAL episode is re-fetched every Monday forever** (parked 2026-09-04, Phase 5 PR #49): the queue is "has no songs yet" with a date floor, so a rerun whose page carries no credits (row 8532, "206: Somewhere in the Arabian Sea", the only one today; ~3 more a year) costs one Firecrawl call a week for good. The durable fix is a marker on `episodes.has_songs_discussed` set by the scrape when a page was read and held nothing — no DDL, but it changes a shared column's meaning. Deliberately not done with the fix; one wasted call a week is cheaper than a meaning change made at 4 am. **Duplicate episode rows are wider than two TAL pairs** (measured 2026-09-04): 73 title-duplicate groups across SOP and TAL; 10 of SOP's 23 songless rows since 2025-12-19 are twins of rows that carry the songs; TAL's 886 (ids 3021/7846) and 887 (3040/7845) exist twice because Taddy dates TAL one day later than the website, so `repair_duplicate_episodes.py` (keyed on that date) cannot merge them. Cosmetic for the playlists (the sync dedups by track id) and tolerated by PR #52's alarm thresholds, but it inflates the public descriptions' episode counts and feeds the songless noise. Needs a dedup plan of its own (which row wins, what moves, what the identity key should be) and Kevin's paste — not a side effect of anything.

- **Saved episodes from Spotify links store the page title, not the episode title** (found 2026-09-04 by PR #54's replay): `scrape_link_meta`'s non-Firecrawl fallback accepts the `<title>` tag when `og:title` is missing, so two saved rows hold `"<episode> - <show> | Podcast on Spotify"` with `source_name = 'Podcast'` (ids 4817, 4818). Taddy returns the correct episode as its top result for both, then the 0.80 title ratio scored against the full stored title (0.719, 0.583) discards it — so they never get a transcript. Fix: a Spotify-specific unwrap in that function mirroring the castro.fm branch (strip the trailing `| Podcast on Spotify`, split `<episode> - <show>` into title and show), plus a re-save of the two rows. Related, also found there: `import_transcripts.taddy_query` retries every `RequestException` five times including 4xx, so a request WE malformed costs five calls before the warning — shared by every show's import, so its own small PR. And PR #53's show gate rejects one correct match where the saved show and Taddy's feed are companion shows ("Incognito Mode" ↔ "Search Engine", 0.222 with a perfect title) — a documented alias pair in `show_config` is the honest fix if it recurs.

## Test gaps (known, dated)
- **SQL statements are only ever run by mocks in `tests/`** (parked 2026-09-02, found while reviewing PR #31): a statement Postgres would reject — a misspelled column, a CHECK violation, a bad placeholder — passes the suite in every module that mocks the cursor (`sync_notion`, `load_entity_batch`, `store`, …). Cheapest fix: a CI step that parses every SQL string with `pglast` and cross-checks column names against the `sql/` migrations; the intake PR did that by hand once. Not a Neon round-trip — CI has no database on purpose. **Grew on 2026-09-03 (Phase 4, PR #43):** the two new run checks in `data_health.py` (`ai_run_completeness`, `ai_run_stuck_loading`) are the most involved SQL in the file — jsonb guards, a `NOT EXISTS` over a set-returning function — and the suite pins them by source text only. Both of the blocking bugs found in review were predicates that read correctly against today's data and wrong against a state that did not exist yet, which executing the query would not have caught either; the builder ran and `EXPLAIN`ed both against Neon by hand, and that evidence lives in commit messages. If a real-Postgres fixture ever lands (a throwaway Neon branch in CI is the natural shape), start with these two.

- **A backfill's Notion sync doesn't fit one step** (parked 2026-09-02): `step_notion_sync` runs under `run_script`'s 600 s timeout, sized for a daily delta of a few entities. The PCHH back-catalogue (2,073 new mentions) needed ~25 minutes; locally it timed out three times (each attempt resumed — the sync is NULL-marker gated — and 987 entities landed in 25 minutes), and the same day's CI run hit the job's 50-minute limit doing the same work. Fix when the next backfill comes: a `--limit` on the sync so one attempt is one bounded chunk, or a longer timeout for `--backfill` runs only. The daily path is unaffected.
